# План CRM v2 — HR-портал с оффер-модулем (проект-«конфетка»)

Концепция: мини HR-портал. Ядро — сотрудник (single source of truth), главная фича — модуль Job Offers (воспроизведение твоего лучшего рабочего кейса), плюс новости, дашборд и AI-ассистент. Стек: FastAPI + PostgreSQL + Alembic (есть) / Vue 3 + TS + Vite + Pinia + Vue Router + Tailwind.

---

## 1. Архитектура данных: единый источник правды

**Ядро — таблица `employees`.** Всё остальное ссылается на неё, ничего не дублирует.

- `users` (уже есть) — только авторизация: email, password_hash, role, is_active. 
- `employees` — профиль: user_id (FK, 1:1), full_name, position, phone, telegram, hire_date, status (active/inactive), avatar_url. Любое поле профиля живёт ТОЛЬКО здесь.
- `offers` — job-офферы: candidate_name, candidate_email, position, salary_note, created_by (FK → employees), status (draft / sent / accepted / declined / expired), public_token (uuid для публичной ссылки), expires_at, timestamps.
- `news` (есть) — + author_id (FK → employees).
- Правило для всех будущих модулей: новая сущность = отдельная таблица + FK на employees. Никаких копий имени/телефона в других таблицах.

**Карточка сотрудника** — витрина принципа: один экран, где профиль + созданные им офферы + его новости. Данные «собираются» JOIN-ами, а не ручным обходом разделов.

**На фронте:** один Pinia-стор на сущность (authStore, employeeStore, offerStore, newsStore). Страницы читают сторы, не хранят локальных копий. Мутация → через стор → все экраны консистентны.

## 2. Карта страниц

### Публичные (без логина)
1. **/login** — вход.
2. **/offer/{token}** — ⭐ публичная страница оффера для кандидата: брендированная, красивая (твоя гордость!), данные позиции, кнопки «Принять» / «Отклонить», состояние «истёк» после expires_at. Единственная публичная страница — и главный вау-экран демо.

### Общие (любая роль)
3. **/dashboard** — виджеты по роли: user видит новости + свой профиль; hr/admin — графики (офферы по статусам, сотрудники по статусу), последние офферы, последние новости.
4. **/news** — лента новостей (карточки, пагинация).
5. **/news/{id}** — просмотр новости.
6. **/profile** — мой профиль: просмотр и редактирование СВОИХ полей (телефон, telegram) → живая демонстрация single source of truth: поменяла телефон → он обновился везде.

### HR + Admin
7. **/employees** — таблица сотрудников: поиск, фильтры (статус, должность), CSV-экспорт, статус-бейджи. Паттерны из твоей рабочей системы.
8. **/employees/{id}** — ⭐ карточка сотрудника: профиль + его офферы + активность. Витрина архитектуры.
9. **/offers** — таблица офферов: фильтры по статусу/дате, статус-пилюли (draft серый, sent синий, accepted зелёный, declined красный, expired оранжевый), действия: посмотреть, скопировать публичную ссылку, архивировать.
10. **/offers/new** — создание оффера: форма (кандидат, позиция, условия, срок действия) + кнопка «✨ Сгенерировать текст с AI» (тезисы → готовый текст приветствия/описания) + превью публичной страницы до отправки.
11. **/news/manage** — создание/редактирование новостей (+ AI-черновик по тезисам).

### Admin only
12. **/users** — управление доступами: список, смена роли, деактивация.
13. **/403** — страница «нет доступа» (для route guards).

Сайдбар группируется секциями и фильтруется по роли (как в референсе): ОБЩЕЕ (дашборд, новости, профиль) / HR (сотрудники, офферы) / АДМИН (пользователи).

## 3. Жизненный цикл оффера (сердце проекта)

draft → sent (генерируется public_token, ссылка уходит кандидату) → accepted | declined (кандидат жмёт кнопку на публичной странице) → expired (фоновая проверка expires_at при запросе). Archive — отдельный флаг.

Бэк-эндпоинты: CRUD /offers (hr/admin), GET /public/offers/{token} (без auth), POST /public/offers/{token}/respond (accept/decline, без auth, идемпотентно), плюс смена статуса на expired при чтении, если срок вышел.

Демо-сценарий для собеседования (репетируем заранее): «HR создаёт оффер → AI генерирует текст → превью → отправка → открываю публичную ссылку в инкогнито → принимаю как кандидат → статус в CRM обновился → виден в карточке сотрудника-автора и на дашборде». 90 секунд, полный цикл, вау.

## 4. Этапы (обновлённые)

- **Этап 0 (бэк, 1–2 вечера):** CORS; таблица employees + миграция + сиды (3 роли, 5–6 сотрудников); защита news; GET/PATCH users; связать news.author_id.
- **Этап 1 (2–3 вечера):** каркас фронта: login, axios-интерсептор с refresh, route guards по ролям, layout с сайдбаром по секциям. 
- **Этап 2 (2–3 вечера):** employees: таблица (поиск, фильтры, CSV) + карточка сотрудника + /profile с редактированием.
- **Этап 3 (3–4 вечера):** ⭐ offers: бэк-модуль целиком + таблица + форма создания + публичная страница по токену + статусная модель. Самый большой этап — дели на два: (3а) бэк + таблица, (3б) публичная страница + respond-флоу.
- **Этап 4 (2 вечера):** дашборд: /stats эндпоинт, графики по офферам и сотрудникам, виджеты.
- **Этап 5 (2 вечера):** AI: POST /ai/draft (тезисы → текст оффера; тот же эндпоинт для новостей), ключ в .env бэка, кнопка в формах.
- **Этап 6 (2 вечера):** полировка: news CRUD UI, тёмная тема, адаптив, README с демо-гифкой, деплой (Vercel + Render/Railway), тестовые логины в README.

После каждого этапа проект показуем. Минимальная витрина = этапы 0–3. 

## 5. Правила «конфетки» (чтобы гордость не съела дедлайн)

1. «Постоянно придумывать и дорабатывать» — ПОСЛЕ деплоя минимальной витрины, не вместо. Идеи в течение разработки → в файл IDEAS.md, не в текущий этап.
2. Один этап = одна ветка = один PR себе = аккуратные коммиты (`feat: offer public page`). История разработки — часть портфолио.
3. Каждое архитектурное решение — строчкой в README (секция Architecture Decisions): «почему employees — ядро», «почему token, а не id в публичной ссылке». Это твои ответы на собеседованиях, записанные заранее.
4. Референс-скриншоты старой системы — только для твоих глаз. В README — свои скрины, свой бренд, свой акцентный цвет.
